> **Высокопроизводительный системный оркестратор проектов, контейнеров и эфемерных Nix-окружений на стыке нативного Rust и встраиваемого LuaJIT.**  
> **Манифест парадигмы абсолютной эфемерности: Хост-система священна и чиста. Захотел — запустил.**

**GRIME** кардинально переосмысливает взаимодействие разработчика с операционной системой, сборочными тулчейнами и зависимостями. Он ликвидирует синдром «работает на моей машине», фрагментацию компиляторов и тяжеловесность контейнеризации. GRIME объединяет математическую герметичность **Nix Flakes**, гибкость изолированных контейнеров **Distrobox** и скорость нативного ядра **Rust** в единый декларативный конвейер данных с субмиллисекундным временем реакции.

Начиная с версии **v1.1.0**, ядро GRIME стало **промышленным сверхнадёжным микроядром (Hardened Resilient Microkernel)**. Вся предметная логика, адаптеры языков и сборочные стратегии полностью вынесены в декларативные динамические модули LuaJIT, а ядро Rust сфокусировано исключительно на управлении жизненным циклом, асинхронном пайплайнинге, супервизии задач, IPC и бескомпромиссной безопасности исполнения.

## 🌟 Философия абсолютной эфемерности (Ephemeral-First)

Традиционный подход к администрированию Linux-систем и разработке ПО устарел:
- Постоянные `sudo pacman -S`, `apt install` или глобальные `pip install` неизбежно превращают операционную систему хоста в «свалку» несовместимых библиотек, конфликтующих версий Python/GCC/LLVM и сиротских пакетов.
- Удаление программ оставляет мусор в `/usr/lib`, `/var` и конфигурационных каталогах.
- Состояние машины со временем деградирует и становится неповторимым.

### 🛡️ Парадигма GRIME: Священная чистота хоста
В экосистеме GRIME операционная система хоста остаётся **кристально чистой и минималистичной**:
1. **Никаких глобальных компиляторов**: Вам не нужно держать установленными GCC 14, Clang 19, Rust, OpenJDK 21, Python 3.12, CMake или Ninja на хосте.
2. **Эфемерный тулчейн на лету**: Интеллектуальный сканер автоматически определяет потребности проекта и собирает код внутри изолированного окружения Nix, которое растворяется сразу после завершения сборки.
3. **Безопасная изоляция**: Любое действие, требующее специфического окружения, направляется либо в эфемерную песочницу Nix, либо в изолированный контейнер Distrobox.
4. **Суверенитет хоста**: Защитные барьеры микроядра гарантируют, что ни один шаг конвейера не сможет повредить системные разделы хоста (`/`, `/usr`, `/etc`, `/nix`).

## ⚡ Принцип «Захотел — запустил» (Just Run / Zero-Friction)

Главная практическая реализация философии эфемерности в GRIME — это концепция **Zero-Friction Execution**:

### 1. Интерактивный перехват в Fish Shell (`command-not-found`)
Вам понадобилась утилита для разовой задачи (`cmatrix`, `cbonsai`, `figlet`, `cava`, `ffmpeg`, `htop`, `ripgrep`, `jq`, `graphviz`)? 
Просто введите её имя в командной строке:

```text
> cmatrix
[Grime] Команда 'cmatrix' не найдена на хосте.
Найдена в репозитории Nixpkgs. Запустить в изолированном окружении? [Y/n]: y
```
- Пользователь нажимает **Enter** (или `Y`) — и утилита мгновенно запускается в чистейшей изолированной песочнице Nix.
- **Никакой установки в систему!** После выхода из программы хост остаётся абсолютно чистым.
- Хотите запустить напрямую без подтверждения? Используйте `grime pkg run cmatrix` или передайте флаг `--yes`.

### 2. Полная поддержка интерактивных TUI и прямое наследование PTY (`Stdio::inherit`)
Благодаря нативному ядру Grime-RS v1.1.0 с каноническим пробросом файловых дескрипторов терминала:
- Любые псевдотерминальные и TUI-утилиты (`cava`, `btop`, `nvim`, `less`, `cmatrix`) работают с полноценной 24-битной цветопередачей TrueColor, поддержкой мыши и без задержек ввода-вывода.

### 3. Интеллектуальный мэппинг команд и нечёткий поиск опечаток (Fuzzy Matching)
- **Умное разрешение пакетов**: Если команда не совпадает с именем пакета Nixpkgs (например, `uname` входит в `coreutils`, а `xargs` — в `findutils`), встроенная база соответствий GRIME безошибочно подберёт нужный пакет.
- **Алгоритм Дамерау-Левенштейна (`grime.fuzzy`)**: Если вы опечатались при вводе команды (`carg` вместо `cargo`), GRIME моментально подскажет правильный вариант:
  ```text
  [Grime] Команда 'carg' не найдена.
  💡 Возможно, вы имели в виду: cargo?
  ```

## ⚡ Ключевые архитектурные возможности

### 1. Эфемерный тулчейн разработки (Auto-Toolchain)
GRIME избавляет разработчика от ручной настройки сборочных сред. Встроенный сканер [`languages/scanner.lua`](modules/languages/scanner.lua) в связке с общими утилитами [`languages/utils.lua`](modules/languages/utils.lua) анализирует исходный код проекта (C++, Rust, Python, Java, Lua, Go) и сборочные манифесты (`CMakeLists.txt`, `Cargo.toml`, `Makefile`, `pom.xml`):
- Автоматически строит точный граф компиляции и выводит список инструментов для `nativeBuildInputs`.
- Бесшовно объединяет авто-тулчейн со специфическими системными библиотеками, объявленными в `app.lua` через `special_dependencies = { "openssl", "raylib", "boost" }`.
- Проекты собираются и запускаются командами `grime project build` и `grime project run` без единого установленного на хосте компилятора!

### 2. Принцип чистого дерева (Zero Dirty Tree)
Сборка проектов происходит в изолированных средах Nix без загрязнения корня репозитория:
- Синтез эфемерных Flake-описаний происходит в изолированном пользовательском кэше (`~/.cache/grime/flakes/<hash>/`).
- Никаких паразитных `flake.nix`, `flake.lock` или `.direnv` в рабочей директории проекта.
- Гарантированная повторяемость сборки на любой машине с установленным Nix.

### 3. Микросервисы и полиглотные приложения (`grime app`)
GRIME предоставляет промышленный жизненный цикл для микросервисов и полиглотных связок:
- Декларативное описание в компактных манифестах `app.lua`.
- Управление демонами: запуск в фоне (`--detach`), мониторинг PID, супервизия жизненного цикла и структурированные логи.
- Поддержка полиглотных стеков: например, C++ вычислительное ядро, обёрнутое в аналитические скрипты Python с передачей данных через потоки или IPC.

### 4. Автономные самодостаточные бандлы (`grime app bundle`)
Команда `grime app bundle <app>` генерирует автономный исполняемый файл в каталоге `dist/`:
- Запекает все runtime-зависимости (включая glibc, интерпретатор Python, динамические библиотеки и ресурсы) в единый переносимый бинарник.
- Готовый артефакт запускается на любом обычном Linux-дистрибутиве без установленного Nix, компиляторов или системных библиотек.

### 5. Бесшовные конвейеры сред (Host ↔ Distrobox ↔ Nix)
GRIME позволяет строить непрерывные конвейеры с переходом границ сред за один вызов:
```bash
grime project cpp init MyGame : box fedora-box : project build : host : project run
```
- Шаги конвейера разделяются двоеточием `:`.
- Бесшовная передача контекста выполнения, переменных окружения и файловых дескрипторов между средами.
- Рубежный модуль `host` безопасно возвращает контекст исполнения на хост-машину.

### 6. Шина состояния StateBus (`grime bus`) и двойной аудит (Git + Nix)
- **StateBus**: Потокобезопасная шина в оперативной памяти демона для обмена метаданными между модулями без хрупкого парсинга stdout. Поддерживает автоматическую RAII-очистку пространства `pipeline.*` после завершения конвейера и персистентное состояние.
- **Двойной аудит**: Команда `grime app diff <app>` одновременно инспектирует как изменения в исходном коде через `git diff`, так и расхождения в структуре собранных пакетов и замыканий Nix через `nix store diff-closures`.
- **Снимки и мгновенный откат**: `grime app snapshot <app> "ревизия"` и `grime app rollback <app>`.

### 7. Сверхнадёжное промышленное микроядро (Hardened Resilient Microkernel v1.1.0)
В нативном ядре Grime-RS реализован комплекс защитных механизмов операционного уровня:
- **Защита IPC от DoS и OOM**: строгий лимит размера передаваемых сообщений 32 МБ с мгновенным отсечением повреждённых сокетных фреймов и защитой от исчерпания памяти хоста.
- **Интеллектуальный супервизор задач (`TaskSupervisor`)**:
  - Защита от ложных таймаутов на долгих шагах сборки (`is_step_active`): пока компилятор или шаг конвейера активно работает, таймаут не прерывает задачу.
  - Автоматическая очистка завершённых задач старше 1 часа (Retention Policy) для предотвращения утечек памяти и дескрипторов.
  - Самовосстановление после отравления блокировок (Mutex Poison Recovery) — сбой отдельного потока не приводит к падению фонового демона `grimed`.
- **Суверенитет файловой системы и защита системных путей**: безусловный запрет любых деструктивных файловых операций над системными директориями (`/`, `/etc`, `/usr`, `/nix`, `/var`, `/boot`, `/root`), а также запрет разыменования симлинков при изменении прав (`chmod`), предотвращающий атаки privilege escalation.
- **Защита от переполнения стека (Stack Overflow Guard)**: жёсткое ограничение глубины обхода при сериализации графов таблиц Lua в JSON (`max_depth = 64`), предотвращающее падения из-за циклических ссылок.

## 🚀 Быстрый старт

### 1. Сборка и установка ядра

#### Через Nix Flake (Рекомендуемый герметичный способ):
```bash
# Сборка статического бинарника без внешних runtime-зависимостей:
nix build .#static

# Или запуск готового dev-окружения:
nix develop
```

#### Классическая сборка через Cargo:
```bash
cargo build --release
```
Бинарные файлы будут скомпилированы в:
- `target/release/grime` — сверхбыстрый CLI-клиент.
- `target/release/grimed` — резидентный фоновый демон.

Установка в пользовательский `PATH`:
```bash
cp target/release/grime target/release/grimed ~/.local/bin/
```

### 2. Запуск фонового демона (опционально)
```bash
# Фоновый запуск сервиса:
grimed --daemon

# Проверка работоспособности ядра и всех модулей:
grime doctor
```
*(Если демон не запущен, утилита `grime` автоматически исполняет команды локально в том же процессе без потери функционала).*

## 💡 Примеры реальных сценариев

### 1. Эфемерный запуск утилит без установки:
```bash
# Одноразовый запуск TUI-утилиты в изоляции Nix:
grime pkg run cmatrix

# Запуск с авто-подтверждением:
grime pkg run --yes ffmpeg -version
```

### 2. Сборка C++ проекта через авто-тулчейн в эфемерном Nix Flake:
```bash
# Интеллектуальный каскад: CMakeLists.txt -> Makefile -> прямой g++/clang++
grime project cpp init FastService
grime nix build FastService
grime project run FastService
```

### 3. Бесшовный конвейер сквозь среды и контейнеры:
```bash
# Создание проекта -> Сборка в контейнере Fedora -> Возврат на хост -> Запуск
grime project rust MicroCli : box fedora-box : project build : host : project run
```

### 4. Создание и демонизация микросервиса:
```bash
# Инициализация сервиса из шаблона
grime app new telemetry-agent --lang rust

# Фоновый запуск с контролем PID и супервизией
grime app run telemetry-agent --detach

# Проверка статуса всех активных сервисов
grime app list

# Остановка сервиса
grime app stop telemetry-agent
```

### 5. Упаковка полиглотного приложения в автономный переносимый бинарник:
```bash
# Компиляция C++ ядра, запекание Python логики и всех зависимостей в dist/polyapp
grime app bundle polyapp

# Запуск готового независимого бандла на любой Linux-машине:
./apps/polyapp/dist/polyapp
```

### 6. Синхронизация состояния через StateBus:
```bash
grime bus set build.target "release-v2" : log INFO "Флаг установлен" : bus get build.target
```

## 📝 Спецификация манифеста приложения (`app.lua`)

Каждое изолированное приложение или микросервис декларируется файлом `app.lua`:

```lua
return {
    -- Идентификация приложения
    name = "compute-worker",
    version = "1.0.0",
    description = "Высокопроизводительный воркер аналитики",
    type = "polyglot", -- cpp, rust, python, java, polyglot, generic

    -- Сборочные инструкции и артефакт
    build = "g++ -O3 src/engine.cpp -o engine",
    artifact = "engine",
    run = "./engine",
    sources = { "src/engine.cpp", "scripts/analyzer.py" },

    -- Авто-тулчейн и специальные зависимости Nixpkgs
    special_dependencies = {
        "openssl",
        "boost",
        "python3"
    },

    -- Настройки фонового режима (демонизации)
    detached = false,
    env = {
        LOG_LEVEL = "info",
        WORKER_THREADS = "4"
    }
}
```

## 🛠️ Состав модулей расширения

Репозиторий включает декларативные модули LuaJIT (`modules/`), каждый из которых реализует специализированную системную область:

- [`modules/pkg.lua`](modules/pkg.lua) — Унифицированный мульти-менеджер пакетов (Pacman, Flatpak, Nix, Distrobox, Cargo), интеллектуальный маппинг команд, нечёткий поиск опечаток и интерактивный Command-Not-Found.
- [`modules/app.lua`](modules/app.lua) — Полный жизненный цикл приложений, демонизация, снапшоты Git, аудит Nix-замыканий и автономный бандлинг.
- [`modules/project.lua`](modules/project.lua) — Оркестрация исходных проектов разработчика, fuzzy-поиск директорий, проверка актуальности mtime.

## 🐚 Совместимость с командными оболочками и интеграция с Fish Shell

### 1. Синтаксис конвейеров
Конвейеры GRIME используют двоеточие `:` как универсальный разделитель шагов:
```fish
grime host : bus set system.mode production : git status : log INFO "Аудит завершен"
```
> **Совет для пользователей Fish Shell:** Символ `:` предотвращает перехват токена `->` оболочкой Fish (который в Fish интерпретируется как перенаправление потока в файл).

### 2. Подключение Command-Not-Found в Fish Shell
Интеграция хука командной оболочки превращает Fish в самовосстанавливающуюся среду разработки с принципом «Захотел — запустил»:

```fish
# Создание функции перехвата в Fish Shell (~/.config/fish/functions/fish_command_not_found.fish):
function fish_command_not_found
    grime pkg not-found $argv
end
```
После этого любая неизвестная команда в шелле будет обрабатываться интерактивным менеджером GRIME:
1. Проверка локальных приложений Flatpak, Grime Apps, Cargo и Nix-профиля.
2. При наличии в Nixpkgs — предложение запуска в изолированном эфемерном рантайме `[Y/n]` с поддержкой TUI.
3. При опечатке — мгновенная подсказка Did-You-Mean через алгоритм Левенштейна.
